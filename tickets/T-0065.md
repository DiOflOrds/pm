## Die drei Festlegungen stehen bereits — sie werden hier nicht neu getroffen

Aus `pm/T-0054`, unverändert übernommen (dort begründet, Klasse B, PM entscheidet selbst):

1. **Der Knopf setzt `geplant_sprint` auf den nächsten Sprint. `prio` bleibt unberührt.**
   „Für den nächsten Durchlauf" ist eine Aussage über den Termin, nicht über Wichtigkeit.
2. **Der Knopf setzt, er sortiert nicht.** Eine eigene Rangliste wäre ein drittes
   Ordnungsfeld neben `prio` und `geplant_sprint` (B033).
3. **Der Vermerk nennt den Urheber** („Mensch via HMI"), sonst meldet `plan_drift` beim
   nächsten Lauf eine Abweichung, deren Ursache niemand mehr benennen kann.

## Definition of Done

1. Knopf je Zeile der Liste aus `pm/T-0064`, über den **vorhandenen** HMI-Schreibpfad
   (`board.EDITIERBARE_FELDER` führt `geplant_sprint` seit SWR-077); PIN-geschützt wie die
   übrigen Schreibwege.
2. Commit-Vermerk „Mensch via HMI"; das Ticket trägt den Urheber der Terminierung.
3. Ein fehlgeschlagener Schreibvorgang lässt das Ticket **unverändert** und meldet das im
   Klartext (Commit-mit-Rücknahme-Muster aus `tickets.py`).
4. ⚠ Gegentest: ein bereits auf den nächsten Sprint terminiertes Ticket ändert sich nicht
   **und meldet das** — „nichts passiert" und „hat nicht funktioniert" müssen
   unterscheidbar bleiben. Ohne diesen Fall ist der Knopf eine Anzeige ohne Aussage.
5. Tests je Zusicherung, Matrix ohne Lücke, alles committet.

keine Priorisierungsfunktion gefunden worden. Gemeint ist vermutlich die **Bedienform**
(Liste, an jeder Zeile ein Knopf). Das ist eine Rückfrage wert, aber **keine Sperre**: es
betrifft die Optik, nicht die Wirkung.
