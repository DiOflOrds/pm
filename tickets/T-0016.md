## Anlass

Brief `platform/N-0002` (E. John, 06:00): Im Server-Log steht zwischen zwei normalen
`200`-Antworten ein mehrzeiliger Traceback:

```
Exception occurred during processing of request from ('192.168.178.164', 51942)
  ...
  File "platform\backend\server.py", line 149, in handle_one_request
  ...
ConnectionResetError: [WinError 10054] Eine vorhandene Verbindung wurde vom Remotehost geschlossen
```

## Befund

**Kein Serverfehler — aber ein echter Mangel im Log.** Die Adresse `192.168.178.164` ist ein
LAN-Gerät (Handy). WinError 10054 heißt: die **Gegenseite** hat die Verbindung hart geschlossen,
während der Server auf die nächste Anfragezeile wartete. Auslöser im Alltag: Bildschirm sperren,
Tab schließen, WLAN wechseln, PWA in den Hintergrund schicken. Der Server hält HTTP-Verbindungen
per Keep-Alive offen — jede so beendete Verbindung erzeugt genau diesen Traceback.

Wirkung: Die Anfrage war ohnehin verloren, der Server läuft weiter, **kein Datenverlust, keine
Fehlfunktion**. Der Schaden ist die Lesbarkeit: Ein Normalvorgang sah aus wie ein Absturz. Das ist
nicht kosmetisch — ein Log, in dem harmlose Tracebacks stehen, macht den nächsten *echten*
Traceback unsichtbar. Genau deshalb behoben statt wegerklärt.

Einordnung: Umsetzungsmangel an bestehender Fläche (Keep-Alive-Betrieb im LAN, SWR-073-Umfeld),
**kein neuer SWR** — gleiches Muster wie B019/B020. Klasse C, hier protokolliert.

## Umsetzung

Zwei Stellen, bewusst beide (Gürtel und Hosenträger — der Abbruch kann auch beim Aufräumen der
Verbindung auftreten, also außerhalb des Handlers):

1. **`Api.handle_one_request`** (dort, wo schon der Ruhe-Zähler für SWR-073 sitzt): fängt
   `ConnectionResetError`, `ConnectionAbortedError`, `BrokenPipeError`, setzt `close_connection`
   und schreibt **eine** Zeile ins Log:
   `[backend] Verbindung zu 192.168.178.164 vorzeitig beendet (ConnectionResetError) — kein Fehler, Anfrage verworfen.`
2. **`RuhigerServer.handle_error`** (neue Serverklasse statt `ThreadingHTTPServer` in `start()`):
   verwirft Verbindungsabbrüche still, reicht **alles andere unverändert** an die
   Standardbehandlung durch.

Die Unterscheidung liegt in einer eigenen Prüffunktion `verbindungsabbruch(fehler)` — eine Quelle
statt zwei Kopien derselben Fehlerliste (Lesson vom 16.08. aus p9/T-0007).

**Absichtlich nicht getan:** kein pauschales `except Exception`. Echte Fehler behalten ihren
Traceback, sonst hätte diese Beruhigung künftige Befunde zugedeckt — dafür gibt es zwei eigene
Tests.

Nebenbefund geprüft und in Ordnung: Der Ruhe-Zähler der Neustart-Wache (SWR-073) wird auch im
Abbruchfall freigegeben (`with`-Block umschließt das `try`) — sonst hätte der Server nach einem
Handy-Abbruch nie wieder selbstständig neu gestartet. Eigener Test.

## Verifikation

- **6 neue Unit-Tests** in `platform/tests/test_backend.py` (`VerbindungsabbruchTest`): Abbruch
  erkannt · echte Fehler nicht als Abbruch · Handler verwirft mit genau einer Zeile · Handler
  lässt echte Fehler durch · Ruhe-Zähler freigegeben · Serverklasse schweigt nur bei Abbruch.
- **Realprobe (Vorher/Nachher)** gegen den echten Server mit dem Symptom aus dem Brief
  (`rfile.readline` wirft `ConnectionResetError` 10054):
  **vorher 2 Tracebacks im stderr — nachher 0**, stattdessen zwei Klartextzeilen; anschließender
  `GET /api/version` liefert 200, der Server bedient also unverändert weiter.
- **205 Tests grün** (vorher 199), Matrix unverändert 83 SWRs / 0 Lücken, 0,00 € API.
